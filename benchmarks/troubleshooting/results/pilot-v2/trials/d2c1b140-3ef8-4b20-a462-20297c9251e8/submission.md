# Submission

## failed_boundary

The failure was at the local SQLite ledger confirmation write, after the provider-transfer operation had returned. `pay()` calls the provider at `app/core.py:52` and then calls `ledger.confirm()` at `app/core.py:53`; the incident traceback reaches `app/adapters.py:78` (`UPDATE payments SET transfer_id ...`) and reports `sqlite3.IntegrityError: database or disk is full` (`incident/stderr.txt:1-10`). Thus this was not an insufficient-funds or request-validation failure, and it was not the provider call timing out; it was the post-provider local receipt/posting commit boundary.

## evidence

The exact operator invocation and payment details are recorded in `incident/report.md:3-16`. The request shape and idempotency identity are implemented in `app/adapters.py:105-115`; the matching recorded success fixture contains POST `/v1/transfers`, key `contractor-payment:milestone-42`, amount 50000, destination `acct_demo_contractor`, and transfer group `milestone-42` (`app/fixtures/success.json:3-23`). The application failed specifically in `confirm` (`incident/stderr.txt:3-10`), after `StripeTransfers.create()` would have returned. `reproduce_incident` deterministically produced the same exit status 1 and traceback in `incident/reproductions/01/stderr.txt`. Direct inspection of `incident/ledger.db` shows balances `(1, 50000, 50000, 2535400)`, payment row `('milestone-42','acct_demo_contractor',50000,1788706800,NULL)`, no posting for that payment, and 121 payments versus 120 postings. The same state is present in `incident/reproductions/01/ledger.db`. The durable intent and reservation behavior is visible in `app/adapters.py:44-61`, while confirmation is intended to be atomic at `app/adapters.py:63-79`; the observed absence of the posting and receipt is consistent with rollback when the later update fails.

## external_outcome

The application reached confirmation only after `StripeTransfers.create()` accepted a response: `app/adapters.py:115-125` requires status 200, matching amount/currency/destination/transfer group, and a `tr_` id before returning, and `app/core.py:53` is the next operation. The matching recorded success interaction (`app/fixtures/success.json:12-23`) identifies the expected accepted transfer as `tr_demo_500`, so the evidence strongly indicates the provider accepted a transfer for this identity before the local write failed. However, the database has no saved transfer id, and the artifacts do not independently query the provider's current record; provider-side durable status should therefore be reconciled by the idempotency key before any repair. Bank settlement is explicitly not established by a transfer response (workspace payment semantics); it is outside this application.

## local_state

The intent exists with the original identity, destination, amount, and creation time: payment `milestone-42`, `acct_demo_contractor`, 50000 cents, created at `1788706800`, transfer_id NULL. The 50000 cents remain reserved: available is 50000, reserved is 50000, contractor is 2535400. There is no `postings` row for `milestone-42`, so locally it is unresolved—not paid/posted—and the reserved funds must not be released or made available. The failure did not create a second payment identity or a local posting.
