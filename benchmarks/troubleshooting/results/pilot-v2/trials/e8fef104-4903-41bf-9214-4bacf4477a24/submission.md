# Submission

## failed_boundary

The failure is at provider-response confirmation/validation in `pay`, not at intent reservation or local posting. The first SQLite transaction reserves the cents and inserts the payment at `app/app.py:40-58`; only after it commits does the code construct the POST with idempotency key `contractor-payment:<payment_id>` (`app/app.py:59-67`). The reproduced run reaches the response-validation rejection at `app/app.py:77-81`, as shown directly by `incident/reproductions/01/stderr.txt:1-8` (and the original `incident/stderr.txt:1-8`). Thus the response supplied by the configured offline transport was not a timeout (which would raise at `app/app.py:73-74`) and was not acceptable: either its status was not 200 or one/more of object, amount, currency, destination, or transfer_group differed. The recorded output does not identify which predicate failed. The receipt-id check and all posting operations are later (`app/app.py:82-97`) and were not reached.

## evidence

The operator inputs are documented in `incident/report.md:3-11`: `milestone-42`, `acct_demo_contractor`, 50000 cents, and `now=1788706800`; the report also records status 1 at line 5. Exact replay with `reproduce_incident` produced the same status-1 traceback in `incident/reproductions/01/stderr.txt:1-8`. SQLite inspection of `incident/ledger.db` returned payment row `(milestone-42, acct_demo_contractor, 50000, 1788706800, NULL)` and no `postings` row for that payment. It returned balances `(id=1, available=50000, reserved=50000, contractor=2535400)`. Aggregate inspection returned 121 payments totaling 2,585,400 cents but only 120 non-NULL receipts, and 120 postings totaling 2,535,400 cents: the 50,000-cent difference matches this one unreceipted payment. The independently replayed database has the same relevant payment row, balances, and absence of posting. Source establishes the ordering: atomic reserve/intent at `app/app.py:40-58`, validation at `77-81`, then atomic posting/balance move/receipt persistence at `86-97`. The public timeout fixture documents the exact expected request/key/body (`app/fixtures/timeout.json:3-14`), while `app/fixtures/success.json:15-24` illustrates the response shape the validator accepts; neither proves it was the unavailable deployment transport artifact used in this incident.

## external_outcome

Known: the application had enough information to construct the exact 50,000-cent request to `acct_demo_contractor`, with idempotency key `contractor-payment:milestone-42` (`app/app.py:62-66`), and the reproduction got as far as rejecting a non-timeout response (`app/app.py:73-81`). The local application is explicitly offline fixture I/O rather than a live provider call (`app/app.py:68-70`), and the deployment transport configuration/actual response is not included (`incident/report.md:13-16`). Therefore the artifacts do not prove that a remote transfer was rejected, accepted, or absent, and do not provide a `tr_...` receipt. In particular, provider acceptance to the connected account remains uncertain; bank settlement would also remain outside the system even if an accepted transfer were later evidenced.

## local_state

The intent is durable but unresolved: `payments.id=milestone-42` has the immutable recorded destination and amount, `created_at=1788706800`, and `transfer_id=NULL`; it has no posting. The $500 was moved out of spendable `available` into `reserved`: available is 50,000 cents, reserved is 50,000 cents, and contractor remains 2,535,400 cents. This is the expected intermediate state caused by the committed first transaction (`app/app.py:40-58`) followed by rejection before the second transaction (`app/app.py:86-97`). No local evidence supports crediting contractor or freeing the reserve.

## reproduction

For an exact deterministic observation, run `reproduce_incident`; it reruns the command recorded at `incident/report.md:7-11` from the pre-command ledger, and reproduction 01 deterministically exits 1 with `Unconfirmed payment response; reconcile` (`incident/reproductions/01/stderr.txt:1-8`). A focused regression test should use a fresh SQLite database initialized to 100000 cents, fixed inputs `milestone-42` / `acct_demo_contractor` / 50000 / 1788706800, and a parsable fixture whose request exactly equals the request at `app/app.py:62-67` but whose `outcome.kind` is `response` and whose response deliberately fails one validator field (for example status 200 with amount 49999, or status 500). Fault it precisely at the response-validation boundary `app/app.py:77-81`. Assert the exact reconciliation exception; exactly one payment row with those original identity fields and NULL transfer_id; zero postings for it; balances available=50000, reserved=50000, contractor=0 on the fresh ledger; and no second reserve on a repeat with the same failing fixture. A complementary retry test may replace the fixture with a matching valid 200 transfer response carrying one `tr_...` id: it must retain the same payment identity and produce exactly one posting/receipt, available=50000, reserved=0, contractor=50000. This tests both no posting on an unconfirmed response and exactly-once local completion after a valid idempotent retry.

## recovery

Do not create another payment ID, alter the stored destination/amount, release the 50,000-cent reserve, or manufacture a receipt. Compare recovery time with the durable `created_at=1788706800`. At the incident's supplied `now`, age is zero and the code's automatic window predicate is satisfied (`0 <= now-created_at < 23*3600`, `app/app.py:59-60`), so an authorized retry should use exactly `milestone-42`, `acct_demo_contractor`, 50000 cents and consequently the same `contractor-payment:milestone-42` key (`app/app.py:64-66`). Persist/credit locally only after a response validates and supplies a `tr_...` receipt, through the atomic completion path at `app/app.py:86-97`. If the response remains unconfirmable, or if recovery is at/after 23 hours (the code requires reconciliation at `app/app.py:59-60`), perform manual provider-side reconciliation using that same durable identity/idempotency key and retain the reserve while outcome is unknown. If reconciliation establishes a transfer receipt, record that one receipt and one posting; until it does, keep the payment unresolved and funds reserved.
