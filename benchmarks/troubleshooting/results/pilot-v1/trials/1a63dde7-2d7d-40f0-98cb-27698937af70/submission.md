# Submission

## failed_boundary

The failed boundary was local SQLite receipt persistence, after the provider-transfer step: `UPDATE payments SET transfer_id = ?` in `app/app.py:96`. It was not an insufficient-funds failure or a request-construction failure. The first ledger transaction (intent plus reservation) completed at `app/app.py:40-57`; the provider response was then processed and the final atomic posting transaction began at `app/app.py:86-96`, where SQLite raised `IntegrityError: database or disk is full`. The captured traceback identifies that exact statement (`incident/stderr.txt:1-8`, identically `incident/reproductions/01/stderr.txt:1-8`).

## evidence

The incident report identifies the inputs as payment `milestone-42`, destination `acct_demo_contractor`, 50,000 cents, and a freshly funded 100,000-cent ledger (`incident/report.md:3-10`). The failed ledger contains `balances = (1, 50000, 50000, 0)`, `payments = ('milestone-42','acct_demo_contractor',50000,1788706800,NULL)`, and no rows in `postings` (queried from `incident/ledger.db`). Thus the intent and reservation survived, while no receipt or posting survived. The exact supplied reproduction produced exit status 1 and the same traceback (`incident/reproductions/01/stderr.txt:1-8`), and its ledger has the same three facts. In code, a request is built with the durable idempotency key at `app/app.py:61-67`; response validation requires a 200 transfer response matching amount, currency, destination, and transfer group at `app/app.py:75-84`, so reaching line 96 means this run got past those checks and had a `tr_` receipt. The available success fixture records `tr_demo_500` and the matching request (`app/fixtures/success.json:8-23`), but it is explicitly synthetic, not a live capture (`app/fixtures/success.json:1-2`).

## external_outcome

The application/reproduction establishes that a provider response passed the application's transfer checks before the local write failed; under the stated semantics, such a response represents provider acceptance to the connected account, not bank settlement. However, the incident artifacts do not contain a provider-side record or a live response body, and the available fixture is synthetic/offline. Therefore the actual remote transfer/receipt state cannot be independently proven from these artifacts (and bank settlement is not proven in any event). It must be reconciled using the same idempotency identity, rather than inferred from the process failure. If the configured response was the supplied success fixture, the response seen by the application would have been `tr_demo_500`; that is not by itself proof of a real provider transfer.
