# Submission

## failed_boundary

The failure was at the provider-response validation boundary in `StripeTransfers.create`, after the transport call and before local confirmation.  `app/adapters.py:105-115` builds/sends the POST, while `app/adapters.py:119-125` validates the returned object; the returned fields did not equal the requested transfer and line 122 raised `NeedsReconciliation("Response does not match the payment")`.  Consequently `pay` never reached `ledger.confirm` (`app/core.py:47-54`).  `app/main.py:51-55` caught that exception and returned exit status 1.

## evidence

The original report records payment `milestone-42`, destination `acct_demo_contractor`, and 50000 cents, and the exact invocation (`incident/report.md:3-16`).  The original stderr records the precise validation error and stack (`incident/stderr.txt:1-10`); `incident/exit-code.txt` is `1`.  The supplied exact reproduction produced the same exit status and error (`incident/reproductions/01/stderr.txt`, and the `reproduce_incident` result).  Its SQLite state has balances `{available: 50000, reserved: 50000, contractor: 2535400}`, payment row `{id: milestone-42, destination: acct_demo_contractor, cents: 50000, created_at: 1788706800, transfer_id: NULL}`, and 120 postings.  The request shape that is intended for this payment is explicitly shown in `app/fixtures/success.json:3-23` (including idempotency key `contractor-payment:milestone-42`, amount, destination, and transfer group); `StripeTransfers` constructs the same mapping at `app/adapters.py:105-114`.  The timeout fixture also documents the intended unresolved-outcome handling (`app/fixtures/timeout.json:3-14`).

## external_outcome

The application/transport boundary did receive a response rather than a timeout: the observed failure is the response-mismatch branch at `app/adapters.py:119-122`, and the replay's request was accepted by `SingleResponse` (a request mismatch would instead raise at `app/adapters.py:139-147`).  That establishes only that the configured playback returned a response which the application could not validate.  It does not establish that the real provider accepted this transfer, nor that it rejected it: there is no valid `tr_...` receipt in the ledger and no provider query artifact.  In particular, a 200 or a provider-looking response with mismatched fields is not a valid transfer confirmation under this application's rule; bank settlement is also outside the evidence and outside this system.

## local_state

The intent and reservation were committed before I/O, as implemented by `app/core.py:47-52` and `app/adapters.py:44-61`.  The failed run therefore left the durable intent for `milestone-42` with the original amount/destination and `transfer_id` NULL, reduced available by 50000 and increased reserved by 50000.  There is no posting for this payment (the reproduction database has 120 postings, matching the pre-existing completed payments), and contractor balance did not increase.  This is the required unresolved state: funds remain reserved; the application did not release them or create a receipt.
