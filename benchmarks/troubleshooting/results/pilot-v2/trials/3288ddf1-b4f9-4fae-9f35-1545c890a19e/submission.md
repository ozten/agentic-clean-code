# Submission

## failed_boundary

The failure is at the outbound provider-transfer transport boundary, after the durable intent/reservation and before receipt validation/local confirmation. `core.pay` calls `ledger.prepare` before I/O (app/core.py:47-52), then `StripeTransfers.create` calls `transport.send` (app/adapters.py:105-115). The configured `SingleResponse.send` raised `TimeoutError` for the timeout fixture (app/adapters.py:139-147), so no response/`tr_...` receipt reached `StripeTransfers`, and `ledger.confirm` at core.py:53 was never called. This is not a failure of the available-funds check or of the local confirmation transaction.

## evidence

The operator command and inputs are recorded in incident/report.md:3-16. The original stderr identifies `Response lost; remote transfer outcome is unknown` and traceback locates the failing call at `app/adapters.py:115`, ending at `SingleResponse.send` line 146 (incident/stderr.txt:1-23). The correlated prepare trace (`global_trace_id` 2afb3e9f-d202-4686-bb57-05013cb3dc36) completed with payment milestone-42, destination acct_demo_contractor, 50000 cents, created_at 1788706800, and null transfer_id (incident/traces/trace-3cbcfb02-0e58-420e-a612-7181a89e21da/trace.json:4-28). The correlated HTTP trace records exactly one intended POST to `/v1/transfers`, amount/destination/group, and `Idempotency-Key: contractor-payment:milestone-42`, with outputs null and TimeoutError (incident/traces/trace-ab29496a-b7ea-4630-99a4-704a74aaac7b/trace.json:4-22). The timeout fixture explicitly matches that request and specifies `kind: timeout` (app/fixtures/timeout.json:3-14). I reran the supplied invocation: reproduction 01 exited 1 with the same TimeoutError; its traces again contain a completed prepare with null receipt and an HTTP send with the same key/error (command output from `reproduce_incident`, and incident/reproductions/01/traces/*/trace.json).

## external_outcome

Known: the application constructed and handed a request for the fixed identity, $500 amount, and fixed destination to its configured transport; its locally recorded outcome was a lost response/timeout. Unknown: whether a real remote provider received that request, accepted one transfer, assigned a `tr_...` id, rejected it, or never received it. In particular, the trace has `outputs: null` (incident/traces/trace-ab29496a-b7ea-4630-99a4-704a74aaac7b/trace.json:16-21), so it is not evidence of provider acceptance, and it says nothing about bank settlement. The source appropriately treats only a status-200, matching transfer response with a valid `tr_` id as a receipt (app/adapters.py:116-125).

## local_state

The intent was committed but is unresolved. Direct SQLite inspection of incident/ledger.db found exactly one `payments` row: `(milestone-42, acct_demo_contractor, 50000, 1788706800, NULL)`; it found zero `postings` rows for that payment. Balances are `available=50000`, `reserved=50000`, `contractor=2535400`. Thus this $500 was removed from available and remains reserved, was not added to contractor, and has no stored receipt. This follows the prepare update/insert ordering (app/adapters.py:44-61); confirmation, which would insert the posting, decrease reserved, increase contractor, and store the receipt atomically, is app/adapters.py:63-79 and was not reached. Reproduction 01's ledger queried identically for milestone-42 and balances, independently reproducing that local state.

## recovery

Do not create a replacement payment or release the 50000 reserved cents. Preserve milestone-42 and its durable amount/destination. If elapsed time from its recorded `created_at=1788706800` is still under 23 hours, the safe automated action is one retry using exactly payment id `milestone-42`, destination `acct_demo_contractor`, 50000 cents, and idempotency key `contractor-payment:milestone-42`; the code's retry policy is explicitly based on intent creation and stops at 23 hours (app/core.py:39-44). On a matching accepted transfer response, atomically confirm that same payment with its returned `tr_...` receipt using the existing confirm path. If the retry window has passed, or the outcome remains ambiguous, require manual reconciliation against that same identity/key; keep the funds reserved throughout. Only a definitive reconciliation outcome should drive any resolution, and nothing in the present evidence justifies making these uncertain funds available.
