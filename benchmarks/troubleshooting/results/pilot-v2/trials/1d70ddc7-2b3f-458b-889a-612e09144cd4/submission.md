# Submission

## failed_boundary

The failure is at the provider-transfer response boundary in `pay`, after the local intent/reservation transaction and before any local confirmation transaction. `app/app.py:40-57` commits (a) the `payments` intent and (b) the available→reserved movement. It then builds the POST request at lines 61-67, reads/checks the configured transport fixture at lines 68-72, and raises `TimeoutError` on a timeout at line 74. Thus neither response validation (lines 75-84) nor the atomic posting/reserved→contractor/receipt transaction (lines 86-96) ran. The original failure says exactly this at `incident/stderr.txt:1-8`; an independent exact-invocation reproduction has the same traceback at `incident/reproductions/01/stderr.txt:1-8` and exited 1. The deterministic timeout fixture identifies the modeled request as POST `/v1/transfers` with idempotency key `contractor-payment:milestone-42` and amount/destination/group 50000/acct_demo_contractor/milestone-42 (`app/fixtures/timeout.json:3-14`).

## evidence

The operator inputs and original command are recorded in `incident/report.md:3-16`. The local source establishes durable identity and request construction: an existing payment cannot change destination or cents (`app/app.py:42-48`), the idempotency key is `contractor-payment:` plus that identity (`app/app.py:61-66`), and the successful-response path is the only path that writes a posting and receipt (`app/app.py:86-97`). Direct SQLite inspection of `incident/ledger.db` found the exact row `payments(id='milestone-42', destination='acct_demo_contractor', cents=50000, created_at=1788706800, transfer_id=NULL)`, zero `postings` rows for that payment, and `balances(id=1)=(available=50000,reserved=50000,contractor=2535400)`. The same three facts were present in the independently produced `incident/reproductions/01/ledger.db`. The original ordinary output also establishes exit 1 and no stdout (`incident/exit-code.txt` contains `1`; `incident/stdout.txt` is empty).

## external_outcome

Known: the application constructed the fixed request represented by the recorded timeout interaction, including the durable idempotency key; the fixture calls its provenance a recorded provider interaction (`app/fixtures/timeout.json:1-14`). The application received no response/receipt: its error explicitly says the remote transfer outcome is unknown (`incident/stderr.txt:1,7-8`), and no `tr_...` identifier was saved locally. Unknown: whether the provider received the request, accepted exactly one transfer, rejected it, or never received it. In particular, the timeout proves neither provider acceptance nor bank settlement. No external provider was contacted during investigation. The successful fixture is only an offline test artifact, although it does show the expected accepted response shape and `tr_demo_500` receipt (`app/fixtures/success.json:12-25`).

## local_state

The incident left a durable unresolved intent for `milestone-42`, immutable destination `acct_demo_contractor`, amount 50000 cents, created_at 1788706800, and NULL `transfer_id` (row described from `incident/ledger.db`). Its 50000 cents remains reserved: balances are available=50000, reserved=50000, contractor=2535400. There is no posting for the payment. This is consistent with the two local transactions in the code: intent/reservation committed before transport (`app/app.py:40-57`), whereas the posting, reserved decrement, contractor increment, and receipt save occur together only after a valid response (`app/app.py:86-96`).

If the payment is still within 23 hours of its durable `created_at`, retry only `milestone-42` with exactly destination `acct_demo_contractor` and 50000 cents, thereby reusing `contractor-payment:milestone-42`; the application expressly permits the retry only when `0 <= now-created_at < 23*3600` (`app/app.py:59-60`) and preserves the existing identity/terms (`app/app.py:42-48`). A provider supporting that idempotency key can return the prior accepted result rather than create another transfer; upon a valid matching receipt the existing atomic confirmation path can post it. If outside that window, follow the code's required manual reconciliation path (`app/app.py:59-60`): reconcile the provider outcome using this same payment/idempotency identity, then record a verified matching receipt if accepted; otherwise retain the unresolved reservation until a documented resolution. In neither branch should uncertain funds be freed or a replacement payment be initiated.
