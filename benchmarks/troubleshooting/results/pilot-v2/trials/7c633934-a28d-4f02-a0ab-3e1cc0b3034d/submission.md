# Submission

## failed_boundary

The failure is entirely on the local durable-intent/reservation boundary, not at the provider boundary. `pay` calls `ledger.prepare(...)` before it computes the retry key or calls `transfers.create(...)` (`app/core.py:47-53`). In `SqliteLedger.prepare`, the balance reservation UPDATE is followed, in the same `with self.db` transaction, by the durable `payments` INSERT (`app/adapters.py:44-61`). The operator's stack trace locates the exception at that INSERT (`incident/stderr.txt:6-10`): `sqlite3.IntegrityError: database or disk is full`. Thus preparation could not complete and execution never reached `StripeTransfers.create` (`app/adapters.py:105-125`) or confirmation (`app/core.py:53`). The exact supplied rerun produced the same exit-1 stack trace in `incident/reproductions/01/stderr.txt`.

The evidence establishes an SQLite write-capacity/storage error at the intent INSERT; it does not establish the physical root cause (actual filesystem capacity, quota, or another SQLite/environmental condition). The database itself reports `PRAGMA integrity_check = ok` in the inspection command output, and a copy written under the permitted scratch area accepted a probe INSERT, so there is no evidence that the on-disk database content is intrinsically corrupt; that copy experiment does not prove the production/incident storage condition is repaired.

The configured CLI command did not request traces (`incident/report.md:9-11`), so there is no HTTP trace artifact or provider receipt to cite.

## external_outcome

For this failed process, the provider transfer interface was not invoked: the observed exception is from `prepare` before the next sequential statement that could call `transfers.create` (`app/core.py:48-52`). Consequently this run did not submit a transfer and produced no `tr_...` receipt. There is also no local receipt because no milestone payment row exists. We cannot independently query or prove the provider's complete historical state from these offline artifacts—for example, they cannot rule out an unrelated prior use of the same idempotency key outside this invocation—but there is no evidence of one. Bank settlement is neither asserted nor inferable; even a provider transfer response would only establish provider acceptance under the stated semantics.

## local_state

The failed transaction left no partial reservation or intent: `milestone-42` is absent from `payments`, absent from `postings`, and its `transfer_id` is therefore absent. The post-incident `balances` row is available 100,000 cents, reserved 0, contractor 2,535,400 cents. This is consistent with rollback of the UPDATE that precedes the failed INSERT because both operations are inside `with self.db` / one transaction (`app/adapters.py:45-60`), and the direct DB observations show no 50,000-cent debit or reservation. Existing historical contractor/posting totals are 2,535,400 cents; they predate and are unaffected by the attempted milestone payment.
