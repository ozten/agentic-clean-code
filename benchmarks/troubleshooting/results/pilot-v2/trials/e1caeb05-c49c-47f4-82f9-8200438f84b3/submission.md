# Submission

## failed_boundary

The failure is local receipt/finalization persistence, not intent reservation and not the outbound-request construction. `pay` commits the intent/reservation transaction at app/app.py:40-58 before doing fixture/provider I/O. It then has passed response validation (app/app.py:71-84) and entered the second transaction (86-87). The failing operation is specifically `UPDATE payments SET transfer_id = ? WHERE id = ?` at app/app.py:96, after it has attempted the posting insert (93) and reserved-to-contractor balance update (94-95). Both the original stderr (incident/stderr.txt:1-8) and exact-environment reproduction stderr (incident/reproductions/01/stderr.txt:1-8) locate the `sqlite3.IntegrityError: database or disk is full` at line 96; the process exits 1 (incident/exit-code.txt contains `1`). The message establishes the SQLite operation failed with that reported error, but does not by itself prove an actual physical disk-capacity cause.

## evidence

The operator inputs are documented at incident/report.md:3-11: `milestone-42`, `acct_demo_contractor`, 50000 cents, now=1788706800. Reproduction 1 reran that invocation and produced the identical line-96 traceback in incident/reproductions/01/stderr.txt:1-8. Inspection of incident/ledger.db shows `payments` row `(milestone-42, acct_demo_contractor, 50000, 1788706800, NULL)`, no `postings` row with payment_id `milestone-42`, and balances `(available=50000, reserved=50000, contractor=2535400)`. The same database query counted 121 payments but only 120 non-NULL receipts and 120 postings totaling 2535400 cents. `PRAGMA integrity_check` returned `ok`. The code explains these observations: the first transaction reserves and inserts at app/app.py:50-57; the second transaction groups posting, balance movement, and receipt update at 86-96. The recorded success fixture specifies the matching idempotency key and payload at app/fixtures/success.json:3-10 and a 200 transfer response with `tr_demo_500`, amount/destination/group at :12-24. The application is explicitly offline fixture I/O rather than a live API client (app/app.py:68-70).

## external_outcome

What is established is that execution got beyond the timeout branch and all response checks: reaching line 96 is possible only after a non-timeout fixture outcome, status/field validation, and a `tr_` receipt at app/app.py:73-84. The available recorded success interaction is a 200 response for exactly this identity and payload, with receipt `tr_demo_500` (app/fixtures/success.json:12-24), so it is strong local evidence of an accepted transfer in the recorded playback. It is not proof that a real provider was contacted or that a bank settled: the implementation reads a local JSON fixture (app/app.py:68-70), and report.md:13 says the deployment transport configuration is not included. Thus any live provider's state is unverified from these artifacts; if a live request did occur, it may have been accepted under `contractor-payment:milestone-42`, but its state must be reconciled under that same identity. Bank settlement is also outside what a transfer response proves.

## local_state

The durable intent exists and its $500 remains reserved: `payments.milestone-42` has the original immutable destination/amount and NULL transfer_id; available is 50000 and reserved is 50000. There is no local posting for it and contractor remains 2535400 rather than being increased by 50000. This is consistent with the first transaction having committed and the second `with db` transaction rolling back as a unit when line 96 failed; it is also directly confirmed by the database rows above and by reproduction database incident/reproductions/01/ledger.db, which has the same milestone row, no milestone posting, and the same balances. The funds therefore are not locally marked paid and must not become available.

## reproduction

Deterministic observed reproduction: invoke `reproduce_incident`; it reruns the controlled command from incident/report.md:9-11 against the pre-command ledger and deterministically returns exit 1 with line-96 `database or disk is full` (observed output in incident/reproductions/01/stderr.txt:1-8). For a self-contained regression test, initialize a temporary SQLite ledger with 100000 cents using `initialize`, install a test-only `BEFORE UPDATE OF transfer_id ON payments WHEN NEW.id='milestone-42'` trigger that `RAISE(ABORT, 'database or disk is full')`, and call `pay` with payment_id milestone-42, destination acct_demo_contractor, cents 50000, now 1788706800, and app/fixtures/success.json. This injects the fault precisely at the final receipt UPDATE, while the fixture controls the otherwise successful 200/tr_demo_500 response. Assert an IntegrityError; assert exactly one payment intent with unchanged destination/cents/created_at and NULL receipt; assert no milestone posting; and assert balances available=50000, reserved=50000, contractor=0 in the fresh-ledger test (plus conservation at 100000). These assertions verify that a finalization write failure rolls back every second-phase mutation but not the already committed reservation. Remove the fault trigger and retry with the exact same id/destination/cents and a time within `0 <= now-created_at < 23*3600` (the gate at app/app.py:59-60). Assert the receipt is tr_demo_500, exactly one posting of 50000 exists, reserved becomes 0, contractor becomes 50000, available remains 50000, and no second payment identity or second reservation is created.

## recovery

First preserve/backup the ledger and repair the local SQLite write-capacity/integrity condition; do not edit balances, delete the intent, or release the 50000 reservation. While within the 23-hour window, retry only `milestone-42` with the exact stored destination `acct_demo_contractor` and 50000 cents. The code both forbids changed amount/destination for an existing identity (app/app.py:42-45) and constructs the provider idempotency key `contractor-payment:<payment_id>` (62-66), so this preserves payment identity and lets an accepted remote transfer resolve to the same receipt rather than duplicate it. Once local writes are reliable, atomically record the verified receipt/posting/balance movement using the existing finalization path. If the retry window has expired or the provider result cannot be verified, leave the funds reserved and perform manual reconciliation keyed to `contractor-payment:milestone-42` (the code itself requires reconciliation outside the window at 59-60); only finalize on a verified matching receipt. Never create a replacement payment ID and never make these uncertain reserved funds available.
