# Submission

## failed_boundary

The failure was at the local ledger confirmation boundary, specifically SQLite `UPDATE payments SET transfer_id = ?` in `SqliteLedger.confirm`, after the provider request had returned. The traceback is `incident/stderr.txt:7-11` and identifies `app/adapters.py:78` with `sqlite3.IntegrityError: database or disk is full`. This is not an insufficient-funds or request-construction failure: `pay` calls the provider at `app/core.py:52`, then calls confirmation at `app/core.py:53`, and the exception is at the latter operation. The provider transport call itself had completed far enough for `confirm` to receive a receipt and execute its preceding statements.

## evidence

The incident report identifies payment `milestone-42`, destination `acct_demo_contractor`, 50000 cents, initial 100000 cents, and invocation time 1788706800 (`incident/report.md:3-10`). The failed process output explicitly places the error in `pay`'s `ledger.confirm` and at `app/adapters.py:78` (`incident/stderr.txt:3-11`). The persisted database contains balances `(available=50000, reserved=50000, contractor=0)`, payment row `('milestone-42','acct_demo_contractor',50000,1788706800,NULL)`, and no postings; the same rows occur in `incident/reproductions/01/ledger.db`. `app/adapters.py:44-61` shows that intent creation reserves funds before I/O. `app/adapters.py:63-79` shows confirmation is one SQLite transaction and that the failing receipt update follows insertion of the posting and the reserved-to-contractor balance update. The absence of those preceding changes in the database is consistent with rollback of that transaction. Running `reproduce_incident` produced exit status 1 and the identical database-full traceback in `incident/reproductions/01/stderr.txt`. The request/response fixtures are synthetic (`app/fixtures/success.json:1-3`), so they are not evidence of the real incident's exact provider response or transfer ID.

## external_outcome

The application got past `StripeTransfers.create`: by `app/adapters.py:115-125`, a normal return requires a 200 response whose body matches amount, currency, destination, transfer group, and has a `tr_...` ID; the subsequent traceback at `confirm` demonstrates that a receipt was returned to `pay`. Under the stated provider semantics, that kind of validated transfer response means the provider accepted the transfer to the connected account. However, the actual response and transfer ID were not recorded (the original run used no `--traces`, and `payments.transfer_id` is NULL), so the evidence cannot independently identify the transfer or verify the provider's current state. Bank settlement is also expressly not established: a transfer response does not prove settlement. It remains possible operationally that the remote action was accepted while the local commit failed; it is unsafe to treat the user-visible failure as proof that no remote transfer occurred.

## local_state

The durable intent exists with the original identity, destination, amount, and creation time: `payments` has `milestone-42`, `acct_demo_contractor`, 50000, `1788706800`, and NULL transfer ID. The ledger has moved 50000 from available to reserved, leaving available 50000 and reserved 50000; contractor is 0. There is no posting. Thus the reserved funds remain correctly non-spendable, but the local receipt and contractor posting were not committed. `confirm` is wrapped in `with self.db` (`app/adapters.py:64-65`), and the database rows show that the failed transaction did not leave a partial posting or balance transfer behind.

## recovery

Do not create a new payment ID, issue a new-key transfer, or release the 50000 reserved cents. First perform an authorized provider reconciliation using the existing identity/key `contractor-payment:milestone-42` and the original amount/destination (or retry within the 23-hour window using that same idempotency key; `app/core.py:39-44` defines that window). If the provider confirms an accepted transfer, obtain its `tr_...` ID and run the existing payment through the idempotent local confirmation path so `confirm` atomically records the one posting and receipt. If the provider cannot establish the outcome, keep the intent and funds reserved and escalate for manual reconciliation; after the automatic window, do not retry automatically. Only after a verified matching provider receipt should the local reserved-to-contractor transition occur, preserving payment identity and preventing either duplicate payment or uncertain funds becoming spendable.
