# Submission

## failed_boundary

The failed boundary in the reported command was the local automatic-retry eligibility check, not a provider transfer call. `pay()` calls `prepare()` and then `retry_key()` before `transfers.create()` (app/core.py:47-53); `retry_key()` rejects an elapsed age outside [0, 23 hours) (app/core.py:39-44). The recorded run's traceback stops at that check (incident/stderr.txt:3-10), so this invocation never reached `StripeTransfers.create()` or the HTTP transport. The unresolved situation is consistent with the earlier lost-response provider boundary represented by `app/fixtures/timeout.json:1-15`, but that fixture is not proof of what the provider ultimately did.

The durable target row is `('milestone-42','acct_demo_contractor',50000,1788620400,NULL)`, observed directly in incident/ledger.db; the age is exactly 86400 seconds. The same database query showed balances `(available=50000,reserved=50000,contractor=2535400)`, zero postings for milestone-42, and 120 total postings. `SqliteLedger.prepare()` reserves before I/O and persists the intent (app/adapters.py:44-61), while `confirm()` is what creates the posting, moves reserved to contractor, and stores the transfer id (app/adapters.py:63-79). The stderr artifact says the failure was `Payment is outside the automatic retry window` (incident/stderr.txt:1, 9-10). A supplied timeout fixture records the exact intended request, including idempotency key `contractor-payment:milestone-42`, amount, destination, and transfer group (app/fixtures/timeout.json:3-15). ## external_outcome

The reported invocation made no provider request, so it establishes nothing new about the provider. The provider's state remains uncertain: there is no transfer_id or local receipt, and the timeout fixture's explicit outcome is `kind: timeout` (app/fixtures/timeout.json:12-15). A lost response cannot distinguish provider rejection/non-acceptance from provider acceptance followed by a lost response. If the fixture represents the prior attempt, it proves only that the local transport observed a timeout, not whether a transfer was created or settled. Even a provider transfer id would establish provider acceptance to the connected account, not bank settlement (README.md:17-21).

## local_state

The intent exists durably for the exact destination and 50000 cents, with created_at 1788620400 and NULL transfer_id. Its 50000 cents remain reserved: available is 50000 and reserved is 50000; contractor is unchanged at 2535400. There is no milestone-42 posting. The failed retry did not alter this state, which follows from the pre-request ordering in app/core.py:47-52 and is also visible in the database row and balances. The payment must therefore be treated as unresolved, not as failed-and-refundable or successfully paid.

The observed result is exit 1 with `Response lost; remote transfer outcome is unknown`; the resulting rows are balances `(50000,50000,0)`, payment `(milestone-42,acct_demo_contractor,50000,1788620400,NULL)`, and no posting. Then rerun against that same database with `--now 1788706800` (and the same fixture). It deterministically fails at `retry_key()` before `SingleResponse.send()`; the existing payment remains unchanged and no second request is made. A regression test should assert: (1) the first request exactly matches the fixture, including key `contractor-payment:milestone-42`, amount 50000, destination and transfer_group; (2) timeout raises/returns the reconciliation error; (3) intent is committed before that error; (4) available decreases by 50000, reserved increases by 50000, contractor and posting count do not change, and transfer_id remains NULL; (5) a retry at exactly 24 hours raises `NeedsReconciliation` before transport and preserves those rows; and (6) a successful response with the same identity (using app/fixtures/success.json) creates exactly one posting, stores `tr_demo_500`, and moves reserved to contractor, with no duplicate posting on repeat.

## recovery

Do not release the 50000 reserved cents and do not create a replacement payment id. Put milestone-42 into manual reconciliation: query the authoritative provider records/idempotency history for the existing key `contractor-payment:milestone-42`, exact amount 50000, and destination acct_demo_contractor.
